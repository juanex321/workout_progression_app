# Shared Project Context (Agent-Agnostic)

Last updated: 2026-02-23
Repository: `workout_progression_app`

## Purpose

Workout tracking app with adaptive progression. User logs sets, then submits muscle-group feedback. The app adjusts upcoming session volume (sets), rep targets, and RIR guidance based on recent performance and feedback.

## Stack

- Python 3.10+
- Streamlit UI (`app.py`)
- SQLAlchemy ORM 2.x (`db.py`)
- SQLite local fallback (`workout.db`)
- PostgreSQL supported via `DATABASE_URL` (Neon used in docs)
- Pandas for some data handling
- Alembic present for migrations

## Core Files

- `app.py`: main Streamlit UI and session state driven workflow
- `db.py`: engine setup, models, `get_session()` context manager
- `services.py`: CRUD/service layer for sessions, sets, feedback
- `progression.py`: set/rep recommendation and deload trigger logic
- `rir_progression.py`: RIR progression and feedback-trend logic
- `plan.py`: session exercise rotation and defaults
- `init_db.py`: initial schema/seed setup
- `migrate_sqlite_to_postgres.py`: migration utility
- `test_set_progression.py`: progression-focused tests (non-pytest style test file also exists: `Test.py`)

## Database Model Snapshot

Defined in `db.py`:

- `Program`
- `Workout`
- `Exercise`
- `WorkoutExercise`
- `Session`
- `Set`
- `Feedback` (muscle-group feedback fields: soreness, pump, workload)

## Progression System (Current Repo Intent)

- Primary adjustment: sets (up/down based on recent feedback patterns)
- Secondary adjustment: reps (increase when targets are consistently hit)
- Intensity guidance: RIR progression from feedback/session history
- Deload path exists (volume/intensity reduction when stress pattern indicates)
- Weights are generally user-driven (not aggressively auto-increased)

Main entry points:

- `progression.py::recommend_weights_and_reps`
- `progression.py::adjust_sets_based_on_feedback`
- `progression.py::should_deload_by_muscle_group`
- `rir_progression.py::get_rir_for_muscle_group`
- `rir_progression.py::calculate_rir_from_feedback`

## Rotation / Plan Notes

In `plan.py`:

- Leg exercise rotation via `LEG_ROTATION`
- Pull main movement rotation via `PULL_MAIN_ROTATION`
- Defaults: `DEFAULT_TARGET_SETS = 4`, `DEFAULT_TARGET_REPS = 10`
- Exercise-specific set defaults in `EXERCISE_DEFAULT_SETS`
- Session composition generated by `get_session_exercises(session_index)`

## Runtime and Env

Database URL resolution in `db.py`:

1. `DATABASE_URL` environment variable
2. Streamlit secrets (`st.secrets["DATABASE_URL"]`)
3. Local SQLite fallback (`sqlite:///workout.db`)

Practical commands:

- Install: `pip install -r requirements.txt`
- Init DB: `python init_db.py`
- Run app: `streamlit run app.py`
- DB check: `python check_db.py`
- Backup: `python backup_db.py backup`
- Restore: `python backup_db.py restore <backup_file>`

## Working Conventions

- Keep UI logic in `app.py`, business logic in `services.py`/`progression.py`
- Use `with get_session() as db:` for DB operations
- Persist app interaction state with `st.session_state`
- Prefer changing progression behavior in progression modules, not inline in UI

## Known Risks / Attention Points

- Multiple progression modules (`progression.py` and `rir_progression.py`) must stay consistent
- Streamlit rerun/session-state interactions can cause subtle UX/state bugs
- Local SQLite and cloud Postgres paths both exist; test both when changing DB logic
- Some docs reference SQLite-first setup while current deployment docs include Neon/Postgres
